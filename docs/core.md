  <app-structure>
    Проект делается на хакатоне: главное — быстро довести до работающего демо,
    не потеряв читаемость. Поэтому архитектура — вертикальные срезы (feature-first)
    на трёх уровнях, без лишних слоёв и абстракций.

    ```
    app/                  роуты App Router — только композиция
    features/{name}/      пользовательский сценарий целиком (вертикальный срез)
      components/         UI этой фичи
      actions.ts          Server Actions — мутации ("use server")
      queries.ts          чтение данных для серверных компонентов
      schemas.ts          валидация входа (Zod, если подключён)
      types.ts            доменные типы фичи
      status.ts           словари фичи: подписи, пороги, цвета состояний
      mock.ts             заглушки данных, пока нет настоящего бэкенда
    components/ui/        общие «глупые» компоненты без знания о фичах
    lib/                  общая инфраструктура: env.ts, клиенты БД/AI/API, хелперы
    proxy.ts              только сессия: без входа — на /login (права — на страницах)
    supabase/             SQL-миграции и сид; применяются через SQL Editor
    ```

    Каталог создаём, когда в нём появляется первый файл; пустых заготовок нет.

    1. Цепочка зависимостей: `app` → `features` → `components/ui` и `lib`.
       Импорт только вправо, обратные запрещены. `lib` не знает о React, роутах
       и фичах; `components/ui` не знает о фичах.
    2. Между фичами прямых импортов нет. Нужно склеить две фичи — композиция
       в `app/` (страница собирает обе). Общий код, нужный обеим, — в `lib/` или `components/ui/`.
    3. `app/` — тонкий слой: `page.tsx` берёт данные из `features/*/queries.ts`
       и раскладывает компоненты. Бизнес-логики и прямых обращений к БД/внешним API в роуте нет.
    4. Чтение — в серверных компонентах через `queries.ts`. Запись — Server Actions
       (`actions.ts`). Route Handlers (`app/api/**/route.ts`) — только для вебхуков,
       стриминга и клиентов вне приложения.
    5. Внешние сервисы (БД, LLM, сторонние API) подключаем один раз в `lib/{service}.ts`;
       фичи получают клиент оттуда. Ключи — только на сервере, через `lib/env.ts`,
       который падает при старте, если переменной нет. В браузер уходят лишь
       `NEXT_PUBLIC_*`, и ничего секретного с этим префиксом не называем.
    6. Сначала заглушка, потом интеграция: фича стартует на `mock.ts` с теми же
       сигнатурами, что у будущего `queries.ts`, — UI и бэкенд разрабатываются
       параллельно, демо работает без ключей.
    7. Barrel-файлов (`index.ts`) нет: импортируем напрямую по пути к модулю.
    8. Имена файлов — по смыслу, без префикса каталога: контекст задаёт путь
       (`features/feed/queries.ts`, не `features/feed/feed-queries.ts`).
    9. Не абстрагируем заранее: общий код выносим в `lib/` или `components/ui/`
       на втором использовании, не на первом. Безымянных `utils/helpers` нет.
    10. Состояние — на сервере и в URL (`searchParams`) по умолчанию; клиентский
        стор (Zustand и т.п.) подключаем, только когда без него не обойтись.

    Структура изменилась — правь эту схему, а не оставляй расхождение с кодом.
  </app-structure>
