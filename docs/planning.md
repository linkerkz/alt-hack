# orch/ — планирование и верификация задач

Стек: **Next.js + Supabase**, формат — хакатон (скорость важнее идеала, но сломанный main недопустим).

## 1. План пишется первым

Перед любой задачей план кладётся в отдельный файл в `orch/plans/`:

```
orch/plans/NNN-short-name.md     # например 003-auth-magic-link.md
```

**План задаёт только направление, а не реализацию.** Никакого кода, точных имён функций и пошаговых инструкций — исполнитель решает сам, как именно сделать.

Шаблон:

```md
# NNN — Название задачи

Статус: todo | in-progress | review | done

## Цель

Что должно получиться и зачем (1–3 предложения).

## Направление

- Какие части затрагиваем (страницы, API routes, таблицы Supabase)
- Ключевые решения / ограничения (например: RLS обязателен, без новых зависимостей)

## Вне рамок

Чего НЕ делаем в этой задаче.

## Критерии приёмки

- [ ] Проверяемый результат 1
- [ ] Проверяемый результат 2
```

Если по ходу работы направление меняется — сначала правим план, потом код.

## 2. Верификация задачи

Задача считается `done` только после прохождения всех уровней:

| #   | Уровень              | Как проверить                                                                                                                             |
| --- | -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Сборка**           | `npm run lint`, `npx tsc --noEmit`, `npm run build` — без ошибок                                                                          |
| 2   | **База**             | Миграции лежат в `supabase/migrations/` и применяются с нуля; на новых таблицах включён RLS; типы перегенерированы (`supabase gen types`) |
| 3   | **Критерии приёмки** | Каждый пункт из плана отмечен `[x]` и проверен руками в `npm run dev` (или на preview-деплое)                                             |
| 4   | **Безопасность**     | Нет `service_role` ключа на клиенте; секреты только в `.env.local` / env Vercel; `NEXT_PUBLIC_` — только для публичных значений           |
| 5   | **Демо-путь**        | Основной сценарий для жюри не сломан (быстрый прокликивающий smoke-тест)                                                                  |

После проверки в конец файла плана дописывается блок:

```md
## Верификация

- Сборка: ok
- Миграции/RLS: ok
- Критерии: все отмечены
- Проверено где: localhost / preview-URL
- Коммит: <hash>
```

и статус меняется на `done`. Если какой-то уровень не пройден — статус остаётся `review`, а причина пишется в этом же блоке.
