# 002 — Dashboard станции (оперативный отчёт)

Статус: done

## Цель

Аналитический экран-отчёт по одной станции для диспетчера: состояние,
эффективность, выполнение плана, операции во времени, проблемы — считывается
за несколько секунд. Не схема станции (её ведёт другой участник) и не Jira.

## Направление

- Новый роут `app/dashboard/[stationId]/page.tsx`, не трогаем заглушку
  `/stations/[stationId]`.
- Новая фича `features/station-console` (термин «Пульт станции» уже в
  словаре `docs/core.md`).
- Переиспользуем индекс эффективности и его пороги/цвета/статусы — выносим их
  в `lib/status.ts` (были в `features/network-map/status.ts`), так как теперь
  нужны двум фичам, а фичи не импортируют друг друга напрямую. `IndexRing`
  переносится в `components/ui/` по той же причине.
- `station-console` не импортирует типы `network-map` — принимает данные
  станции через собственный структурный тип `StationSnapshot` (форма данных
  на границе фичи), с которым реальный `Station` совместим без приведения
  типов. Склейка происходит в `app/dashboard/[stationId]/page.tsx`.
- Данные, которых нет в модели (операции/Gantt, выполнение плана,
  статистика смены, история индекса, часть «требует внимания») — мок в
  `features/station-console/mock.ts`, детерминированно выводится из реальных
  полей станции.

## Вне рамок

Схема станции, drag-and-drop задач, бэкенд задач/ролей, расчёт индекса по
формуле, realtime, база данных.

## Обновление после merge с main

На main независимо появились своя дизайн-система «Classical»
(`components/ui/*`, `components/ui/tone.ts`, см. `docs/ui.md`) и настоящая
фича `features/station-console` (пульт ДСЦС: схема станции, сценарий
инцидента) — по тому же пути, что и этот dashboard. При слиянии:

- Фича переименована в `features/station-dashboard`, чтобы не конфликтовать
  с `features/station-console`.
- `lib/status.ts` удалён: статус/цвета теперь берутся из
  `components/ui/tone.ts` (общий для всех фич), пороги индекса — в
  собственном `features/station-dashboard/status.ts` (как и у network-map,
  по паттерну «status.ts — словарь фичи»).
- Все 8 компонентов переписаны на компоненты дизайн-системы (`Card`,
  `Kicker`, `Heading`, `IndexValue`, `StatusBadge`, `StatusGlyph`, `Metric`,
  `Meter`, `Table`, `ButtonLink`) вместо самодельных классов Tailwind.
- `StationSnapshot` (структурный тип вместо импорта `Station`) не изменился —
  реальный `Station` по-прежнему совместим с ним напрямую.

## Сеть переехала в БД — что стало реальным

`network-map` перевела станции/участки/поезда на Supabase (`stations`,
`sections`, `train_stops`, `dispatch_areas`, `incidents` — таблицы, не моки).
Так как dashboard получает станцию через `getStation()` из `network-map` и
не хранит собственной копии данных, часть показателей стала реальной без
единой правки кода фичи — просто по архитектуре (структурный тип,
композиция в `app/`):

- **Реальные** (колонки `stations`/`incidents`, все станции): индекс
  эффективности, загрузка путей, среднее отклонение от графика, число
  конфликтов, количество поездов, список активных сбоев в «Требует внимания».
- **Остаются мок** (нет таблицы под них ни у одной станции, кроме демо-пульта,
  и там не как единый отчёт): операции/Gantt, разбивка выполнения плана,
  статистика смены (кроме `avgDelayMinutes` — он реальный), история индекса.
  Формулы в `mock.ts` используют реальные поля станции как вход, поэтому
  картина у каждой станции своя, а не одна и та же на всех.
- Осознанно не делаем по-другому для станции демо-пульта (`almaty-1`, у неё
  есть реальный `track_plan`): единообразие важнее точечной доработки одной
  станции — остальные 37 всё равно показали бы мок, разный подход сбивал бы
  с толку сильнее, чем честный мок везде.
